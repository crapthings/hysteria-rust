# Fake-IP Linux release 压测（2026-11-12）

本文先记录批量提交前的基线，再记录同日有界批量提交的对照结果。

基线只测试客户端 Fake-IP DNS 处理与缓存持久化。没有启动服务器、TUN、网络 DNS
监听器或修改系统网络设置，也没有访问 jp1。基线新增的是可重复的测试和结果记录，
不改变服务端配置、Hysteria 协议或前一轮持久化实现。

结论：缓存命中处理很轻；新域名的整表持久化仍有明显写放大，并发时出现排队。
受限写入和目录权限失败后的保守恢复策略通过测试。这些结果支持继续评估增量
持久化，但不构成生产网络 DNS 延迟或长期可靠性保证。

## 环境与方法

- Linux ARM64 容器，Docker Linux VM 内核 `7.0.14-linuxkit`；宿主机 Apple M1 Max。
- Rust 1.91.1，仓库原始 release 配置：codegen-units=1、thin LTO、strip=symbols，
  没有覆盖优化参数；测试二进制的 `debug_assertions` 为 false。
- 使用 Docker named volume 中的私有临时目录，不使用 tmpfs。虚拟磁盘和宿主机
  缓存会影响结果，不能视作裸机或 jp1 的磁盘性能。
- 测试二进制 SHA-256：
  `12ff35b34c3fb9ae1dbcf6eb72dd867e19ff92f333076993033c5ea9f4d737f2`。

每个容量点使用独立子进程，先写入并加载既有映射，再执行：

1. 64 个连续新域名查询。
2. 16 个线程，每线程 8 个新域名，共 128 个突发冷查询。
3. 对一个已有域名重复 2048 次缓存命中查询。
4. 关闭并重新加载，核对条目数和既有编号。

**三组都显式设置 maxEntries=65536**，保证新增空间；起始 4096 条的案例不代表
默认 4096 容量已满后仍能新增。分别从 4096、16384、64000 增长到
4288、16576、64192 条。测试直接调用实际 `FakeDns::answer`，使用 A 查询，
计时包含解析请求、分配/查表、必要持久化及响应编码；不包含构造测试请求、校验
响应、Tokio 调度队列、系统 DNS、网络传输、TUN 或 QUIC。

## 结果

| 起始条目 | 连续冷查询 p50 / p95 | 16 线程冷突发 p50 / p95 | 后续热查询 p95 | 192 次新增的逻辑快照写入量 |
| --- | ---: | ---: | ---: | ---: |
| 4096 | 1.234 / 1.677 ms | 1.284 / 89.968 ms | 1.167 μs | 26.578 MB |
| 16384 | 1.952 / 2.713 ms | 2.159 / 119.172 ms | 1.125 μs | 104.435 MB |
| 64000 | 4.909 / 6.698 ms | 73.741 / 200.897 ms | 1.167 μs | 406.130 MB |

64k 案例的最终缓存约 2.118 MB，仅新增 192 个域名就序列化并提交了约 406 MB
逻辑快照数据。新域名需要串行持久化，线程调度与互斥锁竞争也会影响突发尾延迟。
该表不能证明每个因素各自贡献了多少延迟。

逻辑写入量根据实际 JSON 快照长度和固定长度的新域名计算，并核对最终文件大小；
它不是块设备实际写入量，不包含文件系统元数据、日志或存储层写放大。
热查询位于突发之后，不能据此宣称混合冷/热并发场景也有相同的 p95。

子进程峰值 RSS 分别为 10876、13876、23484 KiB，包含初始化、测试驱动及线程，
不是完整代理客户端的内存用量。CPU 统计来自 `/proc/self/stat`，时钟粒度为
10 ms；很短的热查询阶段可能显示 0 或 10 ms，不能解释为零 CPU 成本。

[完整原始数据与限制](benchmarks/2026-11-12-fake-ip-linux-release.json)。每种规模只运行
一组固定数量请求，没有覆盖长时间运行、生产负载变化、不同文件系统或不同硬件。

## 真实存储失败与恢复

在独立子进程中分别验证：

- **文件大小限制**：已加载缓存后，仅将该子进程的软文件大小上限降到 16 字节，
  在该子进程中忽略 SIGXFSZ，使实际写入返回 EFBIG。父进程的限制和信号配置不变。
- **目录无写权限**：使用非 root 子进程，将其私有测试目录改为 0500，触发实际
  EACCES；测试结束恢复权限。没有更改用户目录或系统目录的权限。

两种场景均确认：

- 新名字返回 SERVFAIL，原缓存文件字节不变。
- 既有名字仍返回原地址。
- 恢复写入条件后，新分配仍保持停止，直到明确重启。
- 重新加载后原名字仍为 ID 1，新的名字使用 ID 2，没有重排或错误复用。

没有在真实存储上制造 ENOSPC、只读挂载、断电或替换后的目录 fsync 失败。
后者仍由前一轮的故障注入测试覆盖。测试目录已清理。

## 复现与后续方向

Linux 上需要 `getconf`、`prlimit` 和 `/bin/sh`。无需 NET_ADMIN；以 root 运行时，
权限失败案例只对子进程降权，并调整其私有临时目录所有者。不要直接调用子进程
辅助测试；让父测试创建和管理隔离目录。

```shell
cargo test --locked --release -p hysteria-cli --lib \
  measure_linux_release_dns_pressure -- --ignored --nocapture
```

可设置 `HYSTERIA_FAKE_IP_BENCH_DIR` 选择测试存储。每组使用其下新的临时目录，
不会覆盖已有缓存。默认测试不运行这组测量。

基线阶段默认容量继续保持 4096，当时建议评估追加日志或有界批量提交：前者减少
每个新名字的整表重写，后者可以合并突发中的多次提交。无论采用哪种方案，都要
保留“持久化后才响应、编号不复用、失败后可判定恢复、旧缓存可导入”的约束。
本轮不直接引入新文件格式或自动淘汰。


## 有界批量提交对照（同日）

客户端将短时间内的新域名合并提交：固定 1 ms 收集窗口、每批最多 64 个名字、
最多 128 个待分配名字（包括正在写入的批次）。同名请求共享预留，文件和父目录
同步成功后才发布映射并响应。旧 v1 文件、编号、默认容量均不变。

相同容器、release 参数和请求规模的单轮对照：

| 起始条目 | 突发 p95：之前 → 批量 | 突发提交：之前 → 批量 | 突发逻辑写入：之前 → 批量 | 串行冷查询 p50：之前 → 批量 |
| --- | ---: | ---: | ---: | ---: |
| 4096 | 89.968 → 3.281 ms | 128 → 9 | 17.855 → 1.259 MB | 1.234 → 2.573 ms |
| 16384 | 119.172 → 4.706 ms | 128 → 8 | 69.760 → 4.362 MB | 1.952 → 3.207 ms |
| 64000 | 200.897 → 8.785 ms | 128 → 8 | 270.890 → 16.933 MB | 4.909 → 5.803 ms |

串行 64 个新域名仍各写一次整表，因收集窗口增加延迟；不能宣称所有查询都加速。
后续缓存命中 p95 为 1.208、1.167、1.167 μs，均未触发落盘。批量版子进程峰值
RSS 为 10716、12640、22872 KiB，不能将单轮差异解释为稳定的内存收益。

批量版以测试专用计数器记录成功快照次数和文件字节数，每次提交多一次 metadata
查询；前一轮按每次快照长度计算。两者均不代表物理磁盘写入量。并发调度、宿主机
缓存和背景活动未控制，结果只支持这组负载的趋势，不是性能保证。

真实 EFBIG、EACCES 与恢复测试再次通过；新增回归覆盖每批上限、未提前发布、
替换后失败、写入线程 panic、排队上限和关闭期间缓存锁的保留。关闭取消尚未开始
写入的请求，等待当前批次完成；文件系统卡住时仍不承诺固定退出时间。

[批量版原始数据](benchmarks/2026-11-12-fake-ip-linux-batched.json)记录被测二进制哈希。
测量后仅做 Clippy 要求的等价分支、引用和测试整数转换整理。

下一步建议先验收应用实际冷/热混合负载与长时间运行；如串行新域名写入仍是瓶颈，
再单独评估追加日志及恢复设计。本次不改变缓存格式或引入地址回收。


验证记录：macOS workspace 测试通过；Clippy 整理后 Fake-IP 定向回归再次通过。
Linux 库测试 154 项通过，CLI 合约 37 项、客户端体验 4 项、路由工具 3 项、
TUN doctor 1 项通过。macOS workspace 与 Linux CLI all-targets 严格 Clippy 通过；
vendored h3 仍输出既有 lifetime 兼容性警告。本轮不据此宣称真实 TUN 网络验收完成。


## 冷热混合负载（同日）

在相同 Linux release 环境中，加载 64000 条映射；8 个线程各查询 64 个新域名，
另外 8 个线程各查询 4096 个已有域名。所有线程使用 barrier 同步开始，热查询每次
结束后休眠 100 μs（不包含在查询延迟中），覆盖不同的已存名字。

- 512 次新域名查询：p50 5.420 ms，p95 5.981 ms，p99 6.489 ms。
- 32768 次已有域名查询：p95 3.334 μs。
- 其中 13914 次在冷查询工作线程尚未结束时开始：p95 3.166 μs，p99 7.167 μs。
- 64 次落盘，逻辑快照约 135.714 MB；最终 64512 条，重启后 512 个新增编号全部一致。
- 查询阶段约 826 ms，驱动与处理合计 CPU 570 ms，子进程峰值 RSS 24092 KiB。

“冷线程尚未结束”不表示每次热查询都与实际文件写入重叠。这只是一次不足一秒的
有界合成负载，不是真实应用、长时间稳定性或端到端 DNS 验收。处理延迟不包含
请求构造、响应校验和线程启动；其他线程的测试驱动会贡献锁竞争。没有修改生产
代码、缓存格式、系统网络或服务。Linux all-targets 严格 Clippy 与该 release 测试通过。

[原始数据与复现环境](benchmarks/2026-11-12-fake-ip-linux-mixed.json)。运行：

```shell
cargo test --locked --release -p hysteria-cli --lib \
  measure_linux_release_mixed_dns -- --ignored --nocapture
```

结果支持已有映射在这组冷写入负载下继续快速查询；新域名仍整表写入，复杂度见
[容量与复杂度说明](fake-ip-capacity.md#complexity-boundary)。下一步仍需真实应用及
长时间验收；若要降低新域名的渐进写入成本，应独立设计追加日志、检查点和恢复协议。


## 持续混合查询与完整重载检查（同日）

保持 64000 初始映射和 16 个线程，8 个冷线程各查询 64 个新名字，每次后休眠 1 秒；
8 个热线程各查询 64000 次已有名字，每次后休眠 1 ms。休眠不包含在处理延迟中，
操作系统调度会延长实际间隔。本轮查询阶段运行 94.153 秒。

| 项目 | 结果 |
| --- | ---: |
| 新域名查询 | 512 次；p50 10.931 ms，p95 16.956 ms，p99 19.055 ms |
| 已有域名查询 | 512000 次；p95 11.958 μs，p99 76.959 μs |
| 冷线程仍活动时开始的已有查询 | 359594 次；p95 11.708 μs，p99 71.583 μs |
| 成功快照提交 / 逻辑字节 | 129 次 / 273563815 字节 |
| 驱动与处理 CPU / 子进程峰值 RSS | 20.660 秒 / 47376 KiB |
| 完整映射重载 | 64000 个原编号及 512 个新增编号全部一致 |

冷线程的活动区间包含休眠，不代表持续文件写入。热样本和重叠样本保存在测试
向量中，会增加 RSS，不能据此判断客户端内存泄漏。查询全部断言成功且反查正确；
重启检查现在比较完整映射表。Linux all-targets 严格 Clippy、release 测试、格式与
差异空白检查通过。本轮仅补测试和说明，保留生产实现及既有未提交工作。

与上一轮短突发的节奏不同，本轮请求更分散，实际合并为 129 批而非 64 批。
主机负载、调度和缓存未控制，不能把两轮延迟差异归因为代码性能变化。
一分钟量级的合成测试不替代真实应用、数小时/数日运行、整机网络切换或断电验证。
