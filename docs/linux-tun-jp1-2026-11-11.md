# jp1 Linux TUN 隔离验收（2026-11-11）

结果：修复一处关闭期间等待握手的问题后，本轮真实 Linux TUN 功能验收通过。
不代表整机 systemd-resolved 接管、真实公网性能或长期运行验收完成。

## 环境与隔离

- AWS Lightsail 东京 `speedtest-jp1`，Ubuntu 24.04，x86_64；内核 `7.0.0-1012-aws`。
- 通过 AWS CLI 读取实例信息并取得临时 SSH 凭据，以 ubuntu 登录、sudo 执行测试。
  没有修改实例防火墙、AWS 端口规则、现有服务或授权密钥文件。
- 测试二进制为当前 dev 工作区交叉编译的 GNU Linux debug 构建，不是发布包。
  SHA-256：`83de7207badc130054a8b48c96d9958a70c5b32d3069f1f624bb4b2c63ec4420`。
- 两个临时网络命名空间，通过 veth 连接；客户端 `192.0.2.1` / `fd42:5000::1`，
  服务端与测试目标 `192.0.2.2` / `fd42:5000::2`。没有连接宿主机出口或配置 NAT。
- 服务端 QUIC 使用 UDP 50000，测试 DNS 使用 TCP 50053，TCP/UDP echo 使用
  50080/50081。DNS 查询的目的端口 53 仅在客户端命名空间中被 TUN 截获，
  没有在宿主机绑定 53 或任何其他测试端口。
- 一次性自签名证书经客户端 CA 配置校验；没有关闭 TLS 验证。
- 原有 443、80、31001–31003 服务端口及对应业务进程保持运行，测试结束复核
  相关 PID 不变。宿主机路由/规则/DNS 在测试前后比对一致。

## 发现与修复

服务器不可达时，发起连接的任务持有客户端状态 mutex 等待 QUIC 握手。
关闭流程设置停止信号后也要取得同一把锁，导致退出超过本次 15 秒验收限时。

`ClientHandle::client` 现在同时等待握手与停止信号，停止信号优先；停止后也不再
返回现有连接。这样 close 可以取得锁完成清理。新增本地回归测试先接收到真实
QUIC 初始包，再要求 close 在一秒内完成，同时验证等待任务返回错误。

修复后重新交叉编译并上传，在 jp1 重跑完整场景，包括正常转发、重启、离线、
出口失效、冲突回滚和强杀残留，全部通过。没有替换 jp1 正在运行的 rc.6 服务。

本地补充验证：128 个库测试通过（1 个忽略）、36 个 CLI 契约测试和 3 个客户端
分流集成测试通过；严格 Clippy 通过。vendor/h3 仍有原有生命周期格式警告。

首轮另有两个测试夹具问题：OpenSSL 默认生成 CA 证书，改为正确的服务端叶证书；
宿主机 IPv6 RA 路由的 `expires` 自然递减，比对时只排除该动态计时字段。
它们没有造成应用代码修改，也不是宿主机路由被更改。
